# Kubernetes 1.35 + CNPG Barman Cloud plugin migration plan

## Codex Review

- **Do not execute unchanged.** The Barman configuration and retention mapping are broadly correct, but A2 must address the known migration switchover deadlock risk on older CNPG releases.
- **1.35.9 is a reasonable conservative target after the prerequisite upgrades.** QNAP’s Helm ceiling is verified; the matrix needs clearer distinctions between installation constraints, tested compatibility and ongoing support.
- **B4/B5 need explicit kubelet drains and a concrete partial-failure recovery procedure.** The Talos dry-run cannot establish compatibility for the entire estate.
- **Strengthen catalog-continuity evidence and restore isolation.** Restore a recorded in-tree backup through post-migration WAL, provide required control traffic, and prevent the drill from modifying the source catalog.
- **Fix monitoring selection and alert blind spots before migration.** Use the plugin’s documented metrics, detect missing telemetry and missed schedules, and retain completed historical Backup records until their compatibility gate.

## Context

On 2026-10-09 ~11:20Z the cluster is on Talos v1.14.2 (all 7 nodes) and **Kubernetes v1.33.13**,
with etcd 3.7.1, Cilium 1.18.14, Kyverno v1.16.4, CNPG 1.27.1, QNAP CSI v1.6.2, Flux 2.8.8 and
KEDA 2.20.1. See `plans/2026-10-08-talos-upgrade-program-plan.md` and
`docs/runbooks/talos-upgrade.md`.

Two issues are open:

1. **In-tree Barman Cloud.** The three trueswarm Postgres clusters still back up with in-tree
   `spec.backup.barmanObjectStore`. CNPG **1.31.0 removes it**, and 1.30.x is the last minor that runs
   it. The owner's rule is stricter: migrate them **before the next CNPG upgrade**, and this plan's
   Kubernetes path needs CNPG upgrades.
2. **Kubernetes 1.33 is end-of-life** (EOL 2026-06-28). The owner wants the upgrade to the latest
   version done now, not by 2026-11-15.

## Approach

Two tracks. **Track A goes first**, per the owner's "before the next CNPG upgrade". Track B's
Cilium hop may run only during Track A's PR wait (A1).

Never overlap any of these with each other or with a node operation:

- an A3 cluster rollout;
- a CNPG operator hop;
- a Kyverno hop;
- a `talosctl upgrade-k8s` run.

All of them restart CNPG pods or admission webhooks.
