- Cilium 1.18.14 (Helm rev 4), Kyverno v1.16.4 (chart 3.6.4), CNPG 1.27.1 (chart 0.26.1);

### Decision D1: migrate on CNPG 1.30.1, after the operator hops (owner-visible change of order)

The issue text says to migrate "before the next CNPG upgrade". The hard deadline is CNPG **1.31.0**.
Two upstream bugs make migrating on **1.27.1** unsafe, and the operator hops fix both:

- **Switchover deadlock** ([cnpg#11032](https://github.com/cloudnative-pg/cloudnative-pg/pull/11032),
  [#11059](https://github.com/cloudnative-pg/cloudnative-pg/pull/11059)).
  - **What happens:** when a WAL-archiver plugin is enabled on an existing cluster with
    `primaryUpdateMethod: switchover`, the old primary cannot finish a clean demotion without the
    sidecar it does not have yet. The cluster deadlocks.
  - **Fixed in:** 1.28.4, 1.29.3 and 1.30.1 only. trueswarm-pg and trueswarm-platform-pg use
    `switchover`.
- **Empty-archive decision.** Below 1.29.3 the operator does not send the `check_empty_wal_archive`
  decision. The plugin then falls back to an on-disk marker
  ([plugin #1009](https://github.com/cloudnative-pg/plugin-barman-cloud/pull/1009), with known
  "Expected empty archive" deadlocks in [#828](https://github.com/cloudnative-pg/plugin-barman-cloud/issues/828)).

So: CNPG 1.27.1 → 1.28.1 → 1.29.1 (still in-tree, which is supported) → k8s 1.34 → CNPG **1.30.1**
→ migrate all three clusters → k8s 1.35. The 1.31 deadline is met with every CNPG minor to spare.

**Alternative if the owner insists on migrating first, on 1.27.1:**
- set `primaryUpdateMethod: restart` on the two switchover clusters in the migration change;
- rehearse first on a throwaway 2-instance 1.27.1 cluster;
- pre-check the empty-archive marker.

Cost: +1–2 h and a residual empty-archive risk.

## Approach

### Rules for the whole program

- **Exclusion windows.** None of these overlaps another or a node operation, from the first mutation
  through the last verification:
  - a Cilium hop;
  - a CNPG operator hop;
  - a Kyverno hop;
  - a `talosctl upgrade-k8s` run;
  - the plugin install;
  - each cluster's migration;
  - any CSI, cert-manager or webhook change.
- **Platform PRs** (workstation-bot) auto-merge ~20–30 min after CI goes green. They are pushed only
  after the previous step is verified, and nothing is pushed while a window is open.
- **The trueswarm Postgres migrations happen outside 01:30–03:30Z**, the ScheduledBackup times.
- **Every hop records the Helm revision before it** (rollback point). A Helm rollback does not restore
  CRDs, and Flux re-applies Git, so any rollback = Git revert + reconcile, not just `helm rollback`.

### Phase M: CNPG backup observability (before any CNPG change; ailab PR)

- **PodMonitors.** Add explicit `trueswarm-pg-metrics`, `trueswarm-platform-pg-metrics` and
  `trueswarm-admin-pg-metrics` in `kubernetes/apps/infrastructure/monitoring/`, following
  `strive-pg-podmonitor.yaml`:
  - label `release: kube-prometheus-stack`;
  - select `cnpg.io/cluster`, port `metrics`;
  - relabel `cnpg.io/cluster` → `cluster`.
- **`backup-chain` rules**, scoped to `namespace=~"trueswarm|trueswarm-admin"`, and gated to primaries
  with `* on(namespace,pod) group_left (cnpg_pg_replication_in_recovery == 0)`:
  - `CNPGWalArchivingFailing`: on the primary, `last_failed_time > last_archived_time` `for: 15m`.
    This is a persistent-state rule, not an `increase()`.
  - `CNPGWalArchiveBacklog`: `cnpg_collector_pg_wal_archive_status{value="ready"} > 5` `for: 30m`.
    It stays quiet when a database is idle, unlike seconds-since-last-archival.
  - `CNPGBaseBackupStale`: `time() - max by (namespace,cluster)` of
    `barman_cloud_cloudnative_pg_io_last_available_backup_timestamp` (in-tree:
    `cnpg_collector_last_available_backup_timestamp`) `> 26h`. Daily schedule + allowance, so a missed
    schedule fires within ~2 h.
  - `CNPGBackupFailed`: the last failed backup timestamp is greater than the last available.
  - `CNPGBackupMetricsAbsent` / target-down: per expected cluster, `absent(...)` `for: 30m`, so
    "quiet" cannot mean "no data".
- **promtool tests** like `cnpg-replication-rules.test.yaml`: failed, stale, absent, idle, and the
  replica-not-firing and switchover cases.
- **Gate:** all 3 clusters' targets are up, the series are fresh, and the rules evaluate and are quiet.
  This captures the in-tree baseline. The plugin series are verified right after each migration.

1. **Inventory first:**
