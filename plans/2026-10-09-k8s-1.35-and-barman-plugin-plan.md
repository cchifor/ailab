# Kubernetes 1.35 + CNPG Barman Cloud plugin migration plan

## Context

On 2026-10-09 ~11:20Z the cluster is on Talos v1.14.2 (all 7 nodes) and **Kubernetes v1.33.13**,
with etcd 3.7.1, Cilium 1.18.14, Kyverno v1.16.4, CNPG 1.27.1, QNAP CSI v1.6.2, Flux 2.8.8 and
KEDA 2.20.1. See `plans/2026-10-08-talos-upgrade-program-plan.md` and
`docs/runbooks/talos-upgrade.md`.

Two issues are open:

1. **In-tree Barman Cloud.** The three trueswarm Postgres clusters still back up with in-tree
   `spec.backup.barmanObjectStore`. CNPG **1.31.0 removes it**, and 1.30.x is the last minor that runs
   it. The owner's rule is stricter: migrate them **before the next CNPG upgrade**, and this plan's
   Kubernetes path needs CNPG upgrades.
2. **Kubernetes 1.33 is end-of-life** (EOL 2026-06-28). The owner wants the upgrade to the latest
   version done now, not by 2026-11-15.

Latest patches today: 1.34.12, 1.35.9, 1.36.5, 1.37.1.

- **Deprecated-API scan.** `apiserver_requested_deprecated_apis` shows only `v1 Endpoints`, which is
  deprecated but not removed, and Cilium's own `v2alpha1 ciliumnodeconfigs`. No series carries a
  `removed_release` ≤ 1.35.
- **Conclusion.** **v1.35.9 is the newest Kubernetes that every installed component supports.** 1.36
  is gated on a QNAP CSI release, Kyverno 1.20 (plus moving 3 ClusterPolicies and 1
  ClusterCleanupPolicy to CEL types), Cilium 1.20 and KEDA 2.21. 1.37 is also gated on CNPG ≥1.31.
  Track A removes the CNPG blocker. Pushing past 1.35 today would mean running the storage driver
  outside its declared support, which puts every Trident PV at risk.

## Approach

Two tracks. **Track A goes first**, per the owner's "before the next CNPG upgrade". Track B's
Cilium hop may run only during Track A's PR wait (A1).

Never overlap any of these with each other or with a node operation:
- an A3 cluster rollout;
- a CNPG operator hop;
- a Kyverno hop;
- a `talosctl upgrade-k8s` run.

All of them restart CNPG pods or admission webhooks.

### Phase 0 — preparation (≈20 min)

1. Open a platform **rollout-freeze issue** (label id 285), with no AI attribution, and message the
   peer session `cloudlab-gitea-ci-runners`. Their A.2 cutover #2175 is merged; ask for its verified
   status before starting. Check that no workstation-bot platform PR is green and approved, since one
   would auto-merge mid-operation.
2. **etcd snapshot** through a survivor with `_out/talosctl-1142.exe`
   (`_out/etcd-snapshots/pre-k8s134-*.db`), plus a manual `talos-backup` job (decrypt check).
3. Baseline with `probes.sh api|pg|alerts`, Flux Ready counts, and `cilium-dbg status` on all 7
   agents.
4. Tooling: download `kubectl` v1.35.9 (the local client is v1.30.10, outside skew for 1.34+) and the
   `kubectl-cnpg` plugin matching each CNPG hop, both into the ops `_out/`.

### Track A — trueswarm Postgres: in-tree Barman → plugin-barman-cloud

**A0. Healthy-archive baseline (gate).** For each cluster:
- `pg_stat_archiver`: `last_archived_time > last_failed_time` and no failure in the last hour;
- `ContinuousArchiving=True`;
- one fresh on-demand in-tree backup: `kubectl cnpg backup <c> --method barmanObjectStore` → `completed`.

Record the latest in-tree backup IDs. The continuity check in A3 compares against them.

**A1. Install the plugin.** Platform PR: new `deploy/components/plugin-barman-cloud/` with a HelmRelease
`plugin-barman-cloud` in **`cnpg-system`**, the operator's namespace as the plugin requires.
- Chart `plugin-barman-cloud` **0.8.1 (v0.15.1)**, from the existing `cloudnative-pg` HelmRepository.
- `crds: Create/CreateReplace`.
- Wire it next to `cnpg-operator` in the same kustomization(s), with `dependsOn` cnpg-operator and
  cert-manager. The chart issues the operator↔plugin mTLS certificates via cert-manager, which is
  installed (v1.20.2).
- Images pinned by digest, controller and sidecar alike.
- Requirements: CNPG ≥1.26 (we run 1.27.1) and k8s ≥1.29.
- Gates: the `ObjectStore` CRD exists, and the plugin Deployment is Ready.
- **No cluster changes yet.** The plugin is inert until a Cluster references it.

**A2. Canary: trueswarm-admin-pg.** trueswarm-admin PR touching `deploy/foundation/` only:
- new `ObjectStore trueswarm-admin-pg-store` (ns trueswarm-admin):
  - `spec.configuration` = the cluster's current `barmanObjectStore`, verbatim (destinationPath,
    endpointURL, endpointCA, s3Credentials, wal/data gzip);
  - `spec.retentionPolicy: 30d`;
- Cluster:
  - delete `spec.backup.barmanObjectStore` and `spec.backup.retentionPolicy`;
  - keep `spec.backup.target`;
  - add `spec.plugins: [{name: barman-cloud.cloudnative-pg.io, isWALArchiver: true, parameters: {barmanObjectName: trueswarm-admin-pg-store}}]`;
- `ScheduledBackup admin-daily`: `method: plugin`, `pluginConfiguration: {name: barman-cloud.cloudnative-pg.io}`;
- keep `serverName` defaulting to the cluster name, so the plugin writes the **same catalog**
  (`<dest>/trueswarm-admin-pg/`) and the in-tree base backups remain usable for recovery and are
  covered by retention.

Merge with the owner-merge automation. The change is one atomic Cluster update, so CNPG does one
rolling restart: replica first, then a switchover. Before merging, make sure both instances are not on
the same node; if they are, delete the replica pod first, per the runbook.

**A3. Verify (per cluster; the gate for the next one).**
1. Both instance pods run the injected `plugin-barman-cloud` sidecar. The Cluster is healthy and
   `ContinuousArchiving=True`.
2. `SELECT pg_switch_wal()` → within 2 min, `last_archived_wal` advances and `failed_count` is
   unchanged. The sidecar log shows the archive.
3. On-demand `Backup` with `method: plugin` → `completed`.
4. `ObjectStore.status.serverRecoveryWindow[<cluster>]`: `firstRecoverabilityPoint` is **at or
   before** the oldest in-tree backup from A0. Seeing it proves catalog continuity.
5. **Restore drill.** Scratch namespace `pg-restore-drill`:
   - default-deny ingress, egress only to versitygw;
   - copy of the backup-storage Secret and `backup-ca`;
   - an `ObjectStore` with the same configuration;
   - a 1-instance `Cluster` with `bootstrap.recovery.source` → `externalClusters[].plugin`
     (`barmanObjectName`, `serverName: <source cluster>`), and **no `plugins` WAL archiver**, so it
     can never write into the source catalog.

   Compare row counts of the three largest tables against the source as of the recovery time, then
   **delete the namespace**: it holds production data.

Then run **A4** for trueswarm-pg and trueswarm-platform-pg, as one trueswarm-admin PR touching
`deploy/platform/`:
- two ObjectStores, `trueswarm-pg-store` and `trueswarm-platform-pg-store`, the same mapping as A2,
  same bucket and distinct serverNames;
- the same Cluster edits;
- **new ScheduledBackups**, closing the base-backup gap: `trueswarm-pg-daily` (`0 15 2 * * *`) and
  `trueswarm-platform-pg-daily` (`0 30 2 * * *`), both `method: plugin` and `immediate: true`.

Re-run A3 for both clusters. Restore-drill trueswarm-pg; it is the largest, at 160 MB.

**A5. Monitoring (closes the alert gap).**
- Enable `spec.monitoring.enablePodMonitor: true` on all three Clusters (trueswarm-admin PR). Add a
  NetworkPolicy ingress rule from `monitoring` to port 9187 in both namespaces; both have
  default-deny-ingress.
- ailab PR, `backup-chain` PrometheusRule:
  - `CNPGWalArchivingFailing`: `increase(cnpg_pg_stat_archiver_failed_count[1h]) > 0` and the last
    failure is newer than the last success;
  - `CNPGWalArchiveStale`: `cnpg_pg_stat_archiver_seconds_since_last_archival > 7200`;
  - `CNPGBaseBackupStale`: the plugin's last-available-backup timestamp is older than 30 h.

  Confirm the plugin metric names from the live `/metrics` before writing rules.
- Gate: all three clusters' targets are up, and the alerts evaluate without firing.

**A6. Historical one-shot Backups.** The ~11 completed `method: barmanObjectStore` Backup CRs in git
are records; CNPG never re-runs them. They stay for now.
- Add a **pre-CNPG-1.31 gate** to the runbook, with two checks:
  - `kubectl get clusters -A -o json | jq '[.items[] | select(.spec.backup.barmanObjectStore)] | length' == 0`;
  - no `method: barmanObjectStore` in any Flux-applied manifest.
- If 1.31's CRD still rejects them, delete them from git then. Flux prunes the CRs, and deleting a
  Backup CR does not touch object-store data.

**Rollback (Track A)** is valid only while CNPG ≤ 1.30. Revert the PR so `barmanObjectStore` returns
and `plugins` goes away. The in-tree archiver resumes on the same catalog.

### Track B — Kubernetes 1.33.13 → 1.34.12 → 1.35.9

Same discipline as the Talos program:
- adjacent minors only;
- one hop at a time, verified before the next;
- push each platform PR only when the previous hop is verified. It deploys within ~20–30 min of going
  green, so timing is controlled by when I push.

**B1. Cilium 1.18.14 → 1.19.8.** This is the only pre-1.34 blocker independent of CNPG, and it may
overlap A1's PR wait. It is a hand Helm hop per the runbook:
`helm --kube-context admin@ai upgrade cilium cilium/cilium --version 1.19.8 -f kubernetes/infra/bootstrap/cilium-values.yaml --set upgradeCompatibility=1.18`.
- Read the 1.19 upgrade notes first, and diff `helm template` (old vs new values) for removed or
  renamed keys.
- Gates: DaemonSets `cilium` and `cilium-envoy` rolled out; `cilium-dbg status` OK on 7/7; DNS +
  ClusterIP + NodePort smoke; Gitea, registry and the Talos API reachable.
- Rollback: `helm rollback cilium`.

**B2. CNPG 1.27.1 → 1.28.1 → 1.29.1.** These start only after Track A completes. Platform PRs:
`deploy/components/cnpg-operator/helmrelease.yaml` goes to chart **0.27.1**, then **0.28.3**.
- Read each minor's release notes for upgrade actions. Each hop rolls every instance of all 5 clusters.
- Gates per hop: the operator is Ready; all 5 clusters `readyInstances == instances` and accept writes;
  the plugin sidecars stay healthy and the WAL archive advances.

**B3. Kyverno 1.16.4 → 1.17.2 → 1.18.2 → 1.19.1.** Platform PRs:
`deploy/components/kyverno/helmrelease.yaml` goes to chart **3.7.2**, then **3.8.2**, then **3.9.1**.
- Keep `generateValidatingAdmissionPolicy: false` and CRDs `CreateReplace`.
- 1.17 deprecates ClusterPolicy/CleanupPolicy, which still work through 1.19. The 3 audit
  ClusterPolicies and 1 ClusterCleanupPolicy stay as they are.
- Gates per hop: admission allow/deny smoke as in P3, the cleanup controller runs, and webhooks are
  healthy.

**B4. Kubernetes → v1.34.12.**
1. Fresh etcd snapshot.
2. `_out/talosctl-1142.exe upgrade-k8s -n 192.168.0.41 --to 1.34.12 --dry-run` and read its
   removed-API and manifest report.
3. The real run. It rolls the apiserver, controller-manager and scheduler one CP at a time, then the
   kubelets on all 7 nodes (restarts, not reboots, so no drains), then CoreDNS and the bootstrap
   manifests. Last time each hop took about 20 min.

Gates:
- every node Ready at v1.34.12, and all 9 CP static pods on v1.34.12;
- etcd 3/3; API writes;
- all 5 CNPG clusters full with writes;
- Flux all Ready (no `kubeVersion` failures);
- Kyverno smoke; Cilium 7/7;
- **QNAP CSI**: provision, attach, write and delete a test PVC on a worker; no
  Trident version-qualification errors in the controller log;
- KEDA ScaledObjects Ready;
- one Gitea CI job passes on a runner.

**B5. Kubernetes → v1.35.9.** Same as B4.
- 1.35-specific checks: kubelet refuses cgroup v1 (verify that Talos runs unified cgroup v2 before
  starting: no `unified_cgroup_hierarchy=0` in either schematic); containerd 2.3.6 is fine; kube-proxy
  is not used (Cilium `kube-proxy-replacement=true`).
- Same gates as B4.

**B6. CNPG 1.29.1 → 1.30.1** (chart **0.29.1**; requires k8s ≥1.34). Same gates as B2. This lands on
the supported CNPG minor, EOL ~Dec 2026.

**B7. Reconcile and record.**
- ailab PR: tofu `kubernetes_version = "v1.35.9"` in infra / agent-nodes / env-pool. Every plan must
  show 0 add / 0 destroy / 0 replace, and the rendered machine config is diffed against live (the P8
  procedure). Update `docs/runbooks/talos-upgrade.md` with the k8s 1.35 hop, the Barman-plugin
  procedure and the pre-1.31 gate. Update the Cilium version notes.
- Close the freeze issue, tell the peer, and update memory.

**B8. Open a tracking issue for 1.36/1.37**, with these gates:
- a QNAP CSI release with `kubeVersion` > 1.35;
- Kyverno 1.20 after migrating the 4 legacy policies to CEL types;
- Cilium 1.20; KEDA 2.21; Flux 2.9;
- for 1.37, CNPG ≥1.31 (unblocked by Track A).

Re-check the matrix monthly. Kubernetes 1.35 is supported into ~2027-02.

**Rollback (Track B).** Kubernetes and CNPG minors are forward-only. Downgrades are unsupported:
storage versions and CRDs move. Recovery is forward-fix; the etcd snapshot is the RPO of last resort.
Cilium and Kyverno can `helm rollback` within their CRD compatibility.

### Order and timing (owner accepts downtime; no soak)

P0 → A0 → A1 ∥ B1 → A2 → A3 → A4 → A3 → A5 → B2 (×2) → B3 (×3) → B4 → B5 → B6 → B7 → B8.
Estimate ≈ 7–9 h, mostly PR CI and bot-merge latency and per-hop gates.
