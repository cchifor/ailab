# ADR 0027 — `gpt-5.6-sol` served from the ChatGPT subscription through a custom LiteLLM provider (temporary)

**Status:** ACCEPTED (2026-09-20), operator-directed: *"keep the option to use the Api Key OPENAI_API_KEY,
but for now enable the option to use the existing litellm openai codex subscription (that is also used by
dsh)"*. Plan and measurements in `plans/2026-09-20-app-model-recovery-plan.md` (Codex-reviewed, one
round). Temporary by design: the API key is the intended steady state; see *Switching back*.
**Relates to:** ADR 0026 (the `realjaynesage` subscription and LiteLLM's `chatgpt/` provider — this
route spends the same seat d), ADR 0022 (model registration: the route, its consumers and its checksum
come from one `model_list`).

## Context

The Strive platform's contextual document-table workflow (`services/workflow/src/worker/document_fields/model.py`)
calls the `ai/litellm` proxy for `gpt-5.6-sol`: **non-streaming** Chat Completions with a strict
`response_format` json_schema, `max_completion_tokens: 32000`, `reasoning_effort: medium`; it
validates `usage.prompt_tokens`/`completion_tokens` as integers, `finish_reason == stop`,
`role == assistant`, a `null` refusal and JSON content, and records usage as billed truth. On
2026-09-20 every such call answered 401: the `OPENAI_API_KEY` in `litellm-cloud-keys` is rejected by
api.openai.com ("Incorrect API key"). The platform's activation agent asked for the key to be
replaced; the operator directed instead that the subscription serve the name for now, with the
API-key path kept.

Measured the same day inside the pinned image (LiteLLM 1.101.0, `ai/litellm-866ff7c6bf-k52sn`):

1. **`chatgpt/gpt-5.6-sol` is accepted** by chatgpt.com/backend-api/codex (streaming chat-completions:
   `{"answer":"OK","n":7}` in 2.4 s, model id echoed). A 116,520-token prompt was answered in 3.7 s.
2. **Non-streaming chat-completions through `chatgpt/` 500** (`Unknown items in responses API
   response: []`): chatgpt.com's `response.completed` carries `output: []` (the message arrives in
   `response.output_item.done`), and the chat→Responses bridge's empty-output recovery misses that
   shape. Streaming works. The consumer is non-streaming.
3. The provider's Responses allow-list **drops `text`** (the caller's `response_format`) and
   `max_output_tokens`. Widened in-process: **`text.format` is accepted and enforced** by the backend
   (strict JSON vs the free-text `answer='OK', n=7` without it); **`max_output_tokens` is rejected**
   (`400 Unsupported parameter`). So one drop is wrong for this consumer and one is right.
4. For a *custom* provider LiteLLM maps params through `OpenAILikeChatConfig`, whose list has no
   `reasoning_effort`; under `drop_params: true` the caller's effort was silently dropped before the
   handler ran. `litellm_params.allowed_openai_params: [reasoning_effort]` carries it through.
5. A chat-completions call takes the Responses bridge only when the model's info says
   `mode: responses`. For `chatgpt/gpt-5.6-sol` that comes from the **remote** model-cost map the pod
   fetches at start; the bundled fallback map has no entry, and the call then falls into the
   OpenAI-SDK chat path against a `/chat/completions` the Codex backend does not serve. Likewise
   `OpenAIResponsesAPIConfig.should_fake_stream()` turns the upstream call into a plain POST for an
   id absent from the map. Both are decided by which map the pod happened to load.
6. LiteLLM's stream wrapper replaces a missing upstream usage block with a token-count **estimate** in
   the same slot it stores a real one; only the bridge iterator's terminal chunk tells the two apart.
7. Side finding, corrected the same evening: between ~13:24 and ~13:30 UTC, `chatgpt/gpt-6-astra`
   requests from freshly started python processes in the litellm pod (the measurement probes) got
   a Cloudflare JS-challenge 403, while `gpt-5.6-sol` from the same processes passed. In the same
   minutes the proxy process itself served `chatgpt/gpt-6-astra` 200 at 13:23:30 and 13:41:40 UTC
   (Loki; those are the only proxy requests for the model in that window), dsh logged no error, and
   at 15:45 UTC fresh processes passed with every header variant tried. What the edge keyed on was
   not established — the probes and the proxy differ in more than one way (process age, connection
   reuse, request history); the route was never observed failing for a real consumer. Recorded so
   the next such probe result is read as "check the proxy's own log lines first".

## Decision

Serve `gpt-5.6-sol` through **`chatgpt-chat/`**, a custom LiteLLM provider owned by this repo
(`kubernetes/apps/apps/ai/chatgpt_chat.py`, `litellm_settings.custom_provider_map`), and keep the
original paid route as **`gpt-5.6-sol-api`** (`openai/gpt-5.6-sol`, `os.environ/OPENAI_API_KEY`,
`num_retries: 0`), unchanged in every parameter. No fallback between them.

The handler is one inner `chatgpt/responses/<model>` call (the `responses/` prefix forces the
bridge regardless of the map; the inner and outer ids are registered in `litellm.model_cost` at
first use so the transport streams natively regardless of the map, at zero cost), always streamed,
inner retries off, under one deadline for call and drain, the upstream stream closed in `finally`.
For a non-streaming caller it drains the bridge's own iterator and rebuilds a `ModelResponse` with
`litellm.stream_chunk_builder`, capped at 4 MiB of content, with **usage taken from the upstream's
`response.completed` block and refused (502) when there is none**. For a streaming caller it
re-yields the bridge's chunks (role stamped on the first). Around the inner call a `ContextVar` is
set, and a wrapper on `ChatGPTResponsesAPIConfig.transform_responses_api_request` re-adds `text`
only while it is set — every other `chatgpt/` call, i.e. dsh's `gpt-6-astra-realjaynesage`, sends the
byte-identical request it sent before (asserted concurrently in the image test). The inner call is
`no-log`, so the proxy records one success per request under the outer provider.

The handler file is **merged into the `litellm-config` ConfigMap** (kustomization `configMapGenerator`,
`behavior: merge`, no name hash) so it sits beside `config.yaml` and a pod that restarts mid-rollout
reads both from the same in-place ConfigMap — it can never see a `custom_provider_map` entry without
the module it names. The `checksum/chatgpt-chat` pod-template annotation (sha256 of the file, gated
by `scripts/check-inline-hashes.py`) rolls the Deployment on a handler edit, as `checksum/config`
does for the routes. Import-time assertions on the upstream seam make a pin bump that moves it fail
the pod start (the old ReplicaSet keeps serving under `maxUnavailable: 0`); the image-level test
`scripts/tests/integration/test_litellm_chatgpt_chat_handler_contract.py` and a proxy startup smoke
run in the pinned image on every PR that touches the route, so that failure shows before merge.

## Consequences and accepted losses

- **`max_completion_tokens` is dropped** at the provider (the backend refuses `max_output_tokens`).
  The backend's own output ceiling is the only generation bound; the handler's retained-memory
  bounds (4 MiB over every delta payload, 262 144 chunks) are the only memory bounds; the
  platform's post-hoc `completion_tokens <= 32000` check bounds what it *accepts*. A streaming
  caller's `include_usage` chunk is the proxy wrapper's own token count, as for every custom
  provider; exact upstream usage is a non-streaming guarantee.
- **A refusal loses its text.** The 1.101.0 bridge carries no refusal payload on its chunks
  (measured), so a refusal item comes back as empty `content` with `refusal: null`, never as an
  answer; the consumer still fails closed (empty content is not its JSON), just not through its
  refusal guard. Revisit on a pin bump; the image test asserts the measured shape.
- **An abandoned stream is closed explicitly.** The bridge iterator's `aclose()` does not reach the
  httpx response (measured with a stalling transport), so the handler closes
  `completion_stream.streaming_response.response` itself at the deadline or on client disconnect.
- **Quota, not dollars.** The route spends reviewer-2 seat d's weekly window, shared with dsh's
  `openai-codex-realjaynesage`; document-table drafts are large (up to 512 K input / 32 K output per
  attempt on the platform side). No gateway-side concurrency cap; exhaustion surfaces as upstream
  429 → `RateLimitError` → 429 to the caller → `model_unavailable`, one attempt. Observe it on
  `reviewbot_llm_usage_percent{persona="codex",seat="d",limit="weekly_all"}` and the seat alerts
  (ADR 0024/0026). `model_info.max_input_tokens: 131072` records the input confirmed live (116,520
  tokens); `enable_pre_call_checks` is off in this estate, so it documents rather than gates.
- The name is reachable by any master-key / virtual-key holder under Open WebUI's External connection,
  the class ADR 0026 accepted for `gpt-6-astra-realjaynesage`. Neither alias has an `api_base`, so
  neither enters the generated Local/dsh pickers.
- The chatgpt.com edge can challenge requests for a model without notice (finding 7 — it did,
  transiently, for probe processes while the proxy's own concurrent requests succeeded; why it
  distinguished them is not established). If the proxy is ever challenged, the route fails fast with
  an `APIError` carrying the challenge HTML, and the first check is the proxy's own log lines for the
  model, not a probe from a fresh process.
- **Rollback** is `git revert` of the merge: Flux applies the previous ConfigMap (routes,
  `custom_provider_map` and the handler key gone) and the previous pod template; the annotations
  move back; the pods roll to the previous config. Nothing else to clean.

## Switching back (the intended steady state)

1. Put the replacement key in `litellm-cloud-keys.sops.yaml`, roll, and prove **`gpt-5.6-sol-api`**
   answers 200 upstream with the platform-shaped body. That alias keeps the OpenAI contract
   permanently; it is never renamed.
2. Point `gpt-5.6-sol` back at `openai/gpt-5.6-sol` + `os.environ/OPENAI_API_KEY` + `num_retries: 0`
   (`scripts/tests/test_litellm_platform_routes.py` admits both shapes for the name, so this is a
   config change, not a test rewrite); regenerate `checksum/config`.
3. Once no route uses `chatgpt-chat/`, remove `chatgpt_chat.py`, the kustomization merge entry,
   `custom_provider_map`, the `checksum/chatgpt-chat` annotation and its hash site, the handler test
   and the workflow steps; mark this ADR superseded.
