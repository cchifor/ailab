## Hub-first compatibility and Pi acceptance boundary

Upgrade and read back the hub before connecting a holder with
`hello.nativeRecovery=2`; older hubs accept only version 1. The new hub accepts
fresh legacy Pi completions that omit `nativeRecoveryVersion`. Those completions
remain unavailable for owned recovery; old receipts are never relabeled as v2.
Dsh v1 receipts remain supported on a holder advertising the v2 superset.

Owned Pi recovery requires a v2 receipt, the same current holder incarnation and
journal, and the pinned profile/workspace/native-home identities. It imports a
retired Relay-owned source into a fresh Relay owner while preserving the original
native session UUID; credentials and communications are newly installed. The
supported recovery case is a retired worker while its holder remains alive,
including a hub restart. **Whole-holder restart containment remains fail-closed.**
An `owned-process-group-only` retention receipt is not independent evidence that
escaped subprocesses died after losing the holder. Never delete retained homes or
receipts, flip readiness, or infer that containment from successful history import.
Unknown tool effects require the explicit, durably recorded operator-authorized
acknowledgement; that acknowledgement does not bypass ownership or format checks.

Keep canary services off until hub/schema readback, exact published holder/Pi
artifact qualification, approval of the exact profiles, stopped-preservation
restaging and managed binding readiness all pass. Keep the existing v0.11.3
connector and credential-renderer pins: the recorded archive/source compatibility
audit supports those unchanged pins, but is not mixed-version live qualification.

[Router AILab PR #2007](https://git.chifor.me/cchifor/ailab/pulls/2007) remains a
separate owner-held change. Its client-owner census and original-principal

## Rollback: restore, fence, reviewed re-pin

A bare image downgrade is unsupported: older binaries may start against newer
schemas, and recovery commands require their exact schema version. Never downgrade
the hub beneath connected holder-v2 sessions. Freeze new admission and use the
reviewed [restore and recovery-fence procedure](relay-researcher-hub-upgrade.md#rollback-migrations-are-forward-only).

For this rollout, restore its **earliest pre-migration generation** to schema 92,
verify counts/ownership/RLS, run `recovery:fence` with a **fresh** generation using
the schema-matching release, and retain that generation in `relay-restore-fencing`.
Only then may a reviewed PR return both application and migration images to
v0.12.1:

```text
registry.chifor.me/relay/control-plane@sha256:177c1af20e5708af2ceb01e4e6360bd0b08a4859f50edad3784257ef74ea350f
```

Restore has H11's established cost: connector and agent keys are revoked, sessions
are ended, undelivered outbox entries are deleted, a new generation ConfigMap is
required, and writes after the backup are lost. Do not delete generation rows,
receipts or native history to simulate compatibility. The older H16/H15 rollback
boundaries still apply to any further downgrade, including H16's prohibition on
bus/membership changes when an older image is incorrectly running on schema 92.
